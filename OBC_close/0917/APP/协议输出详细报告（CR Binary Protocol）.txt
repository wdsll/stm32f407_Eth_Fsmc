## 5. 协议输出详细报告（CR Binary Protocol）

## 5.1 当前协议帧结构（基于实现反推）

单帧格式：

```text
Byte0   : SOF = 0xA5
Byte1   : TYPE
Byte2   : LEN (payload长度)
Byte3   : SEQ (8-bit, 自增)
Byte4.. : PAYLOAD
ByteN-2 : CHK (从 SOF 到 payload 末尾逐字节 XOR)
ByteN-1 : EOF = 0x5A
```

特性：

- 优点：轻量、易实现、帧边界清晰。  
- 代价：XOR 校验抗误码能力有限；无转义机制时，丢字节后重同步依赖 SOF/EOF 扫描。

## 5.2 帧类型与负载定义

### TYPE = 0x01（`CR_LOG_MON`）

`LEN = 10`：

| 字段 | 类型 | 缩放/单位 |
|---|---|---|
| t_ms | u16 | ms（由 u32 饱和到 65535） |
| vout | i16 | Q10（值=raw/10，单位V） |
| iout | i16 | Q10（A） |
| err  | i16 | Q10（V） |
| f_cmd | u16 | raw*10Hz（即编码前 `f_cmd_hz/10`） |

### TYPE = 0x02（`CR_LOG_EVT_BEGIN`）

`LEN = 8`：


| 字段 | 类型 | 缩放/单位 |
|---|---|---|
| id | u16 | 事件ID（u32 饱和） |
| iout_from | i16 | Q10 A |
| iout_to | i16 | Q10 A |
| vout_pre | i16 | Q10 V |

### TYPE = 0x03（`CR_LOG_EVT_END`）

`LEN = 14`：

| 字段 | 类型 | 缩放/单位 |
|---|---|---|
| id | u16 | 事件ID（u32 饱和） |
| pass | u8 | 1=pass,0=fail |
| rsv | u8 | 保留 |
| dt_ms | u16 | 总历时（饱和） |
| settle_ms | u16 | 稳定时间（饱和） |
| vmin | i16 | Q10 V |
| vmax | i16 | Q10 V |
| maxerr | i16 | Q10 V |

## 5.3 编码策略说明

- 浮点到定点：`Q10`（乘以 10 后转 `int16`）。
- 范围保护：
  - `q10_from_float()` 将超范围值饱和到 `int16` 上下限；
  - `u16_sat_from_u32()` 将 `u32` 饱和到 `65535`。

## 5.4 风险分析

1. **时间戳仅 16 位**：大于 65.535s 后饱和，无法支持长时段连续分析。  
2. **频率编码分辨率 10Hz**：一般足够，但精细调试可能不足。  
3. **XOR 校验弱**：对部分多比特错误检出能力不足。  
4. **阻塞发送**：高频日志时可能影响控制周期。  
5. **协议版本位缺失**：后续升级兼容性弱。

## 5.5 升级建议（Protocol V2）

建议新增 `proto_ver=2`，并保留 V1 兼容期：

- 校验升级：XOR -> CRC16-CCITT。  
- 时间戳升级：`u16 t_ms` -> `u32 t_ms`。  
- 新增 `flags` 位图（fault/burst/precheck/pfc_ready 等上下文位）。  
- 可选 `source_id`（多板/多通道场景）。  
- 发送方式改为 DMA 队列化，避免阻塞控制线程。  
- 增加 `TYPE=0x7F` 能力查询帧（协议版本、字段集、缩放参数）。

## 6. 建议实施路线（可落地）

## Phase-1（1~2 周）：结构固化

1. 头文件全局变量整改（去 `static` 误用）。  
2. 状态机动作与转移解耦（先不改功能，仅改组织）。  
3. 新增状态迁移日志（旧协议可继续用）。  
4. 加入基础 KPI（tick drop、状态驻留时间、fault 次数）。

## Phase-2（2~4 周）：协议与验证

1. 协议 V2（CRC16 + 32位时间 + flags）并保留 V1。  
2. 建立离线解码与一致性回放脚本（输入串口日志 -> 还原状态时间线）。  
3. 建立“状态覆盖测试矩阵”（正常上电、AC 丢失、VBUS 跌落、Burst 进出、故障恢复）。

## 7. 本次评审的直接回答（针对提问）

> “是否还需要继续完善框架和状态机？”

**需要，而且建议继续。**

当前项目功能链已经成型，但从“能跑”到“长期稳定可扩展”之间还差两步：

1. **框架层**：解耦状态逻辑与硬件动作，完善调度可观测性。  
2. **状态机层**：切换到更显式的事件-转移模型并加强 fault 分级恢复。
