## 0. 问题定位（一句话）

`HW/src/llc_control.c:307` 的 STANDBY 出口要求 `g_adc_multi.vbat_v >= BATTERY_PRESENT_V(10.0V)`。
VBT 是 240k/4.7k 分压且**软件无偏置**（`adc_raw_to_voltage` 直算），空载 `vbat_v ≈ 0V`，因此状态机永远停在 `MAIN_STEP_STANDBY`，`pfc_enable()` 永不被调用。

`START` 命令本身不查 vbat，所以**唯一硬阻塞点就是这一行**。其余为无电池后暴露的连带问题。

## 1. 完整阻塞链与影响面

| 编号 | 位置 | 无电池时行为 | 是否必须改 |
|---|---|---|---|
| **P0** | `llc_control.c:307` STANDBY 出口 | `vbat_v≈0 < 10V` → 卡死 STANDBY | **必须** |
| P1 | `llc_control.c:336` CC→CV | `vbat_v≈0` 永远进不了 CV，CC 跑到 8h 超时 | 建议（想验证 CV 才需要） |
| **P1** | `llc_control.c:379` **CV 完成判据** | `vbat_v≈0` 恒假；**且 `iout_a` 被钳零 → `iout<=1A` 恒真** | **必须**（见补丁 G） |
| P2 | `pfc_control.c:38` `pfc_enable` AC 门控 | 上电初期 AC RMS 窗口未满（`ac_vol_v=0`）→ 误报 `FAULT_AC_INPUT_RANGE` | 建议 |
| P2 | `serial_console.c:289` 看门狗 10s | 观察过程需持续敲键，否则自动 STOP | 建议放宽 |
| P2 | `main.h:85` `LLC_ENTRY_V=350V` | 264V 输入时预充峰值 ≈373V > 350V，PFC 未起环即放行 LLC | 建议一并修 |
| P2 | `main.h:107-108` CC/CV 超时 | 实际为 8h / **3h**（注释误写"调试值 3s"），台架等待不现实 | 建议（见补丁 H） |

**结论**：必须改的是 **P0（补丁 B）+ CV 完成判据（补丁 G）**。
只改 P0 就能进 CC 态、验证建压与 LLC 起振；但若同时做了补丁 C（CC→CV 切 vout）而没做 G，CV 态会"空载假完成"误跳 FINISHED。
P1 的 CC→CV 是为了能观察到 CV 态跳变；P2 是台架易用性与既有缺陷。

## 2. 开关定义

### 补丁 A — `App/include/main.h`

**插入位置**：`main.h:95` 之后（`#define IOUT_OCP_A (24.0f)` 下面那个空行处），紧邻 `CHARGE_*` 段落之前。

```c
/* ========================================================================
 * 台架联调模式（无电池 / 假负载）
 *   1 = 旁路 vbat 接入判据，允许 START 后直接进入 PRECHARGE→CC，
 *       用于不接电池验证 PFC 建压(320V→390V)、LLC 起振、继电器时序、LED。
 *   0 = 量产行为：必须有电池(vbat >= BATTERY_PRESENT_V)才放行。
 * ------------------------------------------------------------------------
 * 【量产固件必须为 0】
 * ======================================================================== */
#define BENCH_NO_BATTERY_MODE   (1U)

/* 台架模式下 PFC 使能的 AC 判据上电宽限：
 * AC RMS 采用 200ms/1000 样本整周期窗口，上电后第一个 RMS 值需
 * 1000/5kHz = 200ms 才有效；期间 ac_vol_v = 0 会被 pfc_enable 误判
 * 为欠范围。给 2000ms 宽限，超时后仍按正常 AC 判据执行。 */
#if BENCH_NO_BATTERY_MODE
#define PFC_AC_GRACE_MS         (2000U)
#endif
```

**同时建议修改**（`main.h:84-85`）：

```c
/* 原：
#define VBUS_MIN_START_V        (350.0f)
#define LLC_ENTRY_V             (VBUS_MIN_START_V)
 */
/* 改为： */
#define VBUS_MIN_START_V        (350.0f)     /* PFC 自身 RELAY_ON→RUN 判据，维持不变 */
#define LLC_ENTRY_V             (VBUS_TARGET_V * 0.98f)  /* 380V*0.98 = 372.4V
                                              * 高线(264V)预充峰值≈373V 会越过 350V，
                                              * 使 PFC 未起环即放行 LLC。抬到 380V 附近
                                              * 可确保"LLC 在 PFC 稳压母线上起振"。 */
```

> 若不改 `LLC_ENTRY_V`，264V 输入台架会看到 `pfc_state` 还在 RELAY_ON 时 `state` 已跳 CC，属可复现的时序缺陷。

### 补丁 G（必须，v1 遗漏项）— `HW/src/llc_control.c:377-383` CV 完成判据

> **本补丁为 v2 新增**。v1 只覆盖了 CC→CV（`:336`），**漏掉了 CV 态的完成判据**，属遗漏，此处补齐。

**CV 态存在两个独立缺陷：**

**缺陷 1 — `vbat_v` 判据恒假**
`:379` 用 `g_adc_multi.vbat_v >= (s_voltage_reference_v - CHARGE_FINISH_VOLTAGE_MARGIN_V)`，无电池 `vbat_v≈0` → 恒假 → 永进不了 FINISHED。

**缺陷 2（更危险）— `iout_a <= 1.0A` 在无电池时恒真**

```c
g_adc_multi.iout_a >= 0 && g_adc_multi.iout_a <= CHARGE_FINISH_CURRENT_A(1.0f)
```

`adc_raw_to_current()` 末尾有负值钳零（`HW/src/adc_dma.c:180`）：

```c
return (i < 0.0f) ? 0.0f : i;
```

→ `iout_a >= 0` **恒真**（永不为负）；空载 `iout_a ≈ 0A < 1.0A` 也**恒真**。
**因此一旦缺陷 1 的 vbat 判据被旁路（例如误用补丁 C 的 vout 替换），CV 态会在 `CHARGE_FINISH_DEBOUNCE_MS(30s)` 去抖后直接跳 FINISHED** —— 这是"空载假完成"，会切断继电器、清掉输出电压，但台架上看起来像"充电成功"。

**原文**：

```c
				else
				{
					if(condition_held(&s_qualification,s_voltage_reference_v>BATTERY_PRESENT_V&&g_adc_multi.vbat_v>=(s_voltage_reference_v - CHARGE_FINISH_VOLTAGE_MARGIN_V)
						&& g_adc_multi.iout_a >= 0 && g_adc_multi.iout_a <= CHARGE_FINISH_CURRENT_A,CHARGE_FINISH_DEBOUNCE_MS))
					{
						enter_state(MAIN_STEP_FINISHED);
					}
				}
```

**方案 G1（推荐）：台架下屏蔽完成判据，禁止假完成**

```c
				else
				{
#if BENCH_NO_BATTERY_MODE
					/* 台架：无电池。vbat≈0 使缺陷1恒假；而 iout_a 被钳 0，
					 * 使缺陷2(iout<=1A)恒真 —— 若旁路 vbat 判据就会"空载假完成"。
					 * 故台架下直接屏蔽完成判据，保持 CV 态至 STOP 或超时，
					 * 避免误跳 FINISHED 而切断继电器、清掉输出电压。 */
					(void)s_qualification;
#else
					if(condition_held(&s_qualification,s_voltage_reference_v>BATTERY_PRESENT_V&&g_adc_multi.vbat_v>=(s_voltage_reference_v - CHARGE_FINISH_VOLTAGE_MARGIN_V)
						&& g_adc_multi.iout_a >= 0 && g_adc_multi.iout_a <= CHARGE_FINISH_CURRENT_A,CHARGE_FINISH_DEBOUNCE_MS))
					{
						enter_state(MAIN_STEP_FINISHED);
					}
#endif
				}
```

**方案 G2（可选）：台架下由串口 `FINISH` 手动触发，用于验证 FINISHED 路径**

在 `llc_control.c` 内部变量区加 `static bool s_bench_force_finish;` 并暴露一个 setter，
CV 态改为：

```c
#if BENCH_NO_BATTERY_MODE
				else if (s_bench_force_finish)      /* 由串口 FINISH 命令置位 */
				{
					s_bench_force_finish = false;
					enter_state(MAIN_STEP_FINISHED);
				}
#endif
```

串口侧在 `execute_command()` 增加分支（同样包在 `#if BENCH_NO_BATTERY_MODE` 内）：

```c

	{
		power_supervisor_bench_force_finish();
		debug_printf("OK FINISH (bench forced)\r\n");
	}
```

> G1 更省事（CV 直接挂到超时）；G2 能验证 `FINISHED` 态的 `outputs_force_off()` + 绿灯行为。按台架要验证的内容二选一，**不要同时启用**。

### CV 态行为分岔对照（台架模式）

| 补丁组合 | CV 态实际行为 | 可否观察 FINISHED |
|---|---|---|
| 只做补丁 C（vbat→vout） | 30s 去抖后**假完成 → FINISHED**（绿灯亮、继电器断开） | 能，但是"空载假完成" |
| 补丁 C + **G1** | `state=4(CV)` 保持，直到 `STOP` 或 `CHARGE_CV_TIMEOUT_MS` → `FAULT_CHARGE_TIMEOUT` | 不能（符合预期） |
| 补丁 C + **G2** | 静止在 CV，输入 `FINISH` 才跳 FINISHED | 能，且由人工显式触发 |
| 不做补丁 C（保持 vbat 判据） | 一直挂 `state=4`，不做 C 就进不了 CV；若已在 CV 则挂到超时 | 不能 |

**推荐**：补丁 C + G1 + H。此时台架完整路径为

```
state 3(CC) → 4(CV)         [补丁 C：vout 判据]
state 4(CV) 保持 30s         [补丁 G1：完成判据屏蔽]
  → FAULT_CHARGE_TIMEOUT     [补丁 H：30s 超时]
红灯亮、继电器断开            [FAULT 的 fail-safe 收敛路径同时被验证]
```

若不想引入故障，在 30s 内 `STOP` 即可回到 STANDBY。

### 补丁 D（P2，建议）— `HW/src/pfc_control.c:36-51`

**作用**：上电 2s 内的 AC 判据宽限，避免 AC RMS 窗口未满导致的误报故障。

原文：

```c
void pfc_enable(void)
{
    if (s_pfc_state == PFC_STATE_OFF) {
			  if ((g_adc_multi.ac_vol_v < PFC_AC_INPUT_MIN_V) ||
            (g_adc_multi.ac_vol_v > PFC_AC_INPUT_MAX_V)) {
            protect_set_fault(FAULT_AC_INPUT_RANGE);
            return;
        }
        /* 闭合 PFC 继电器, NCP1654 开始工作 */
```

替换为：

```c
void pfc_enable(void)
{
    if (s_pfc_state == PFC_STATE_OFF) {
#if BENCH_NO_BATTERY_MODE
        /* 台架：上电 PFC_AC_GRACE_MS 内 AC RMS 窗口可能未刷新(200ms 窗口)，
         * 跳过 AC 判决先合继电器；RUN 态由 pfc_is_ready() 持续复查 AC。 */
        const bool ac_grace = (g_ms < PFC_AC_GRACE_MS);
        if (!ac_grace)
#endif
        if ((g_adc_multi.ac_vol_v < PFC_AC_INPUT_MIN_V) ||
            (g_adc_multi.ac_vol_v > PFC_AC_INPUT_MAX_V)) {
            protect_set_fault(FAULT_AC_INPUT_RANGE);
            return;
        }
        /* 闭合 PFC 继电器, NCP1654 开始工作 */
```

> **注意**：`ac_grace` 只在宽限期内跳过判决，之后恢复正常门控；且 `pfc_is_ready()` 仍每 1ms 复查 `ac_vol_v ∈ [165,264]`，所以宽限期过后若 AC 真异常，仍会在 RUN 态被拦。
> **若不想引入 `bool` 局部变量**，可简化为直接内联 `if ((g_ms >= PFC_AC_GRACE_MS) && (条件))` 的形式。

## 6. 仍需实测确认的两点

1. **VBT 悬空行为**：`adc_startup_check()`（`main.c:174-178`）只检查 `vbt_raw >= ADC_RESOLUTION(4095)` 上限饱和，**不检查 0**。若台架上 VBT 网络悬空导致 `vbt_raw` 漂到较大值（自噪或浮空），`adc_startup_check` 仍会通过，但 `bat=xx V` 的显示会误导。建议实测时记录 `STATUS` 打印的 `bat` 与 `raw_bat` 值：
   - 若 `bat` 稳定 ≈0V → 一切正常，补丁 B 的旁路足够；
   - 若 `bat` 漂移且 `vbt_raw` 接近饱和 → 需在硬件侧给 VBT 加下拉，或在 `adc_startup_check` 增加下限判据。

2. **CC 态 1.5s 输出建立超时是否触发**：`llc_control.c:340` 的判据是 `vout_v <= OUTPUT_RELAY_MIN_V(10V)` 且已过 `OUTPUT_START_TIMEOUT_MS(1500ms)`。无电池空载时输出端由 EC3/EC4 经 LLC 保持高压，理论上 `vout_v` 远大于 10V 不会触发。但**若 LLC 起振失败**（例如 `LLC_EN` 引脚宏错位，见下节），输出端会放电到 10V 以下，1.5s 后报 `FAULT_OUTPUT_START_TIMEOUT`。这可作为 LLC 是否真正起振的间接判据。

## 9. v2 新增发现：`iout_a` 钳零导致完成判据在空载下恒真

`HW/src/adc_dma.c:172-181`：

```c
float adc_raw_to_current(uint16_t raw)
{
    float v_adc = ((float)raw * VREF_ADC) / (float)ADC_RESOLUTION;
    float v_offset = VREF_ADC / 2.0f;  /* NSI1312 零电流基准 = VDD/2, 待标定 */
    float i = (v_adc - v_offset) / (ISHUNT_OHM * IAMP_GAIN);
    return (i < 0.0f) ? 0.0f : i;      /* ← 负值钳零 */
}
```

**推论**：
1. `g_adc_multi.iout_a >= 0` 在任何情况下**恒真**，该判据形同虚设；
2. 空载时 `v_adc ≈ v_offset`（NSI1312 零电流输出 = VDD/2）→ `i ≈ 0` → `iout_a <= 1.0A` **恒真**；
3. 故 CV 完成判据的三个子条件中，**只有 `vbat_v` 那一条在真正起筛选作用**。

**对量产代码的提示（超出本补丁范围，建议单独立项）**：
`iout_a >= 0` 这条判据本意应是"排除负电流（电池倒灌）"，但因钳零而不可能触发。
若需保留该语义，应在 `adc_raw_to_current()` 中改为**返回带符号值**，由上层判断极性；或增加一个 `iout_raw_signed` 字段。当前实现下，CV 完成仅靠 `vbat + 30s 去抖` 判定，**充电电流是否真降到 1A 以下完全没有被验证**——这是一个独立于台架模式的逻辑缺陷，接电池后也应复核。

## 11. 致命缺陷：FAULT 是终态，`CLEAR` 是空动作

### 11.1 证据链

**（a）出口被 `#if 0` 关闭** — `HW/src/llc_control.c:299-312`：

```c
void power_supervisor_tick_1khz(void)
{
	/* Commands arrive through the transport-independent supervisor API. */
	if (g_charger_state == MAIN_STEP_FAULT) {
		outputs_force_off();
#if 0   // `!protect_fault_active_hw()` 因 protect.c `#if 1` 恒真，**纯无人干预的"自动恢复"仍是死代码** |
		if(!s_enable_requested&&!protect_fault_latched()&&!protect_fault_active_hw())
		{
			g_fault = FAULT_NONE;
			enter_state(MAIN_STEP_STANDBY);
		}
#endif
		return;                              /* ← 直接返回，下方 switch 永不执行 */
	}
```

**（b）穷举所有 `enter_state(MAIN_STEP_STANDBY)` 调用点** — 全部来自 `grep -an "enter_state(" HW/src/llc_control.c`：

| 行号 | 所在位置 | 从 FAULT 可达？ |
|---|---|---|
| 225 | `power_supervisor_init()` | 仅上电时 |
| 308 | `#if 0` 块内 | ❌ 已被条件编译排除 |
| 330 | switch → `MAIN_STEP_PRECHARGE` case | ❌ 在 `return` 之后，永不执行 |
| 343 | switch → `MAIN_STEP_CC` case | ❌ 同上 |
| 371 | switch → `MAIN_STEP_CV` case | ❌ 同上 |
| 399 | switch → `MAIN_STEP_FINISHED` case | ❌ 同上 |
| 404 | switch → `default` case | ❌ 同上 |

→ **从 FAULT 出发，唯一可达的 `enter_state(STANDBY)` 是上电初始化那次。软件层面无任何出口。**

**（c）`protect_clear_fault()` 不清状态机** — `HW/src/protect.c:65-76`：

```c
void protect_clear_fault(void)
{
    gpio_bit_set(HARD_FAULT_CLR_PORT, HARD_FAULT_CLR_PIN);
    delay_ms(CLEAR_PULSE_MS);                  /* 10ms 忙等 */
    gpio_bit_reset(HARD_FAULT_CLR_PORT, HARD_FAULT_CLR_PIN);
    delay_ms(CLEAR_RELEASE_SETTLE_MS);         /* 5ms 忙等 */
    if (!protect_fault_active_hw()) {          /* 因 #if 1 恒 false → !false = true，必定进入 */
        s_fault_latched = false;
        g_fault = FAULT_NONE;                  /* ← 清锁存与故障码，但不碰 g_charger_state */
    }
}
```

**（d）`protect_set_fault()` 不清使能标志** — `protect.c:78-83`：

```c
void protect_set_fault(fault_type_t f)
{
    s_fault_latched = true;
    g_fault = f;
		power_supervisor_enter_fault();        /* → enter_state(FAULT)，outputs_force_off() */
}
```

注意：进入 FAULT 后 `s_enable_requested` **仍为 true**，因此 FAULT 态下 `power_supervisor_requested()` 返回 true，`CLEAR` 会先被 `"ERR STOP before CLEAR"` 拦住。

### 11.2 台架上的实际死循环

`CC` 或 `CV` 超时（本次配置 **8s / 3s**）→ `protect_set_fault(FAULT_CHARGE_TIMEOUT)` → 进 FAULT：

```
[FAULT]  fault=12 (FAULT_CHARGE_TIMEOUT), state=7
  STOP   → "OK STOP"                        （清 s_enable_requested）
  CLEAR  → "OK CLEAR"                       （清 s_fault_latched + g_fault）
                                             但 state 仍 = 7 (FAULT)
  START  → "ERR fault active; STOP then CLEAR"   ← 因 g_charger_state == MAIN_STEP_FAULT
  STOP → CLEAR → START → 依然 ERR ...
```

`ERR fault active; STOP then CLEAR` 这句提示本身就是**误导**——操作员照做也出不来，只能掉电复位。

### 11.3 为什么本次台架**必然**踩中

本次落地配置 `main.h:117-118`：

```c
#define CHARGE_CC_TIMEOUT_MS            (8U * 1000U)     /* 8s */
#define CHARGE_CV_TIMEOUT_MS            (3U * 1000U)     /* 3s */
```

配合补丁 G1（台架下 CV 完成判据被屏蔽为 `(void)s_qualification;`），产生如下必然后果：

```
进入 CV 态
  → 完成判据已被屏蔽，CV 无事可做
  → 3 秒后 elapsed_reached(s_state_started_ms, CHARGE_CV_TIMEOUT_MS) 成立
  → protect_set_fault(FAULT_CHARGE_TIMEOUT)
  → 进入 FAULT，且无法退出
```

**即：只要跑到 CV，3 秒后必然卡死，必须重新上电。** 如果 `CC→CV` 未在 8s 内达成（例如 LLC 起振慢），则更早在 CC 就卡死。

**迭代测试基本无法进行。**

### 11.4 修复方案

#### 方案 1（推荐，最小改动，只动 1 个文件）

`HW/src/llc_control.c:302-311`，把 `#if 0` 替换为受 CLEAR 驱动的出口：

```c
	if (g_charger_state == MAIN_STEP_FAULT) {
		outputs_force_off();
		/* 仅在操作员已 STOP（清使能）且 CLEAR 已清干净（锁存+故障码）后，
		 * 才允许退出 FAULT。这不是"无人干预自动恢复"——两个条件都必须
		 * 由显式命令满足，因此保留了原注释担心的安全性。 */
		if (!s_enable_requested && !protect_fault_latched() && (g_fault == FAULT_NONE)) {
			enter_state(MAIN_STEP_STANDBY);
		}
		return;
	}
```

> **注意 tab 缩进**：该区域为一个 tab（`^I`）层级，`power_supervisor_tick_1khz` 的函数体。

**安全性论证**（为什么三个条件不可能被自动满足）：

1. 刚进 FAULT 时 `s_fault_latched == true` → 条件不成立，**不会**一进故障就自己跑出来；
2. `protect_set_fault()` 不清 `s_enable_requested`，FAULT 态下 `power_supervisor_requested()` 仍为 true → 必须**先 `STOP`**；
3. `g_fault` 只在 `protect_clear_fault()` 里被清为 `FAULT_NONE` → 必须**再 `CLEAR`**；
4. 三个条件同时满足**只能**由 `STOP` + `CLEAR` 两条显式命令促成，不存在无人干预路径。

**该方案不动串口层一行代码，且 CAN 迁移后自动受益**（CAN 发 STOP + CLEAR 走同样路径）。

#### 方案 2（备选，需新增 API）

在 CLEAR 分支显式回退状态，并在 `llc_control` 暴露接口：

```c
/* llc_control.h */
void power_supervisor_exit_fault_if_clear(void);   /* 供 CLEAR 命令调用 */
```

```c
/* llc_control.c */
void power_supervisor_exit_fault_if_clear(void)
{
    if ((g_charger_state == MAIN_STEP_FAULT) &&
        !s_enable_requested && !protect_fault_latched() && (g_fault == FAULT_NONE)) {
        enter_state(MAIN_STEP_STANDBY);
    }
}
```

```c
/* serial_console.c CLEAR 分支 */
else
{
    protect_clear_fault();
    power_supervisor_exit_fault_if_clear();
    debug_printf("OK CLEAR\r\n");
}
```

方案 2 的语义更显式，但要改两个文件 + 头文件；方案 1 更省。**两者效果等价，推荐方案 1。**

### 关于 #9 的说明（不需要改逻辑，只加注释）

`serial_console.c:211`：

```c

- `protect_fault_active_hw()` 因 `protect.c:53` 的 `#if 1 return false` **恒假**；

### 不修 #7 时的操作规避

若暂时不改码，台架上必须：

1. **避免触发任何故障**：在 8s（CC）/ 3s（CV）超时前主动敲 `STOP`，赶在超时之前回到 STANDBY；
2. 每次 START 后立刻准备 STOP，CV 态**只有 3 秒窗口**；
3. 一旦看到 `state=7`，接受"必须重新上电"这个事实。

> 这种规避方式基本等于"每个充电循环手动掐停"，只能验证建压与 LLC 起振，**无法验证 CC→CV→(FINISHED) 的完整迁移**。

### 另外两处会干扰台架的门限（未落地）

1. **`LLC_ENTRY_V` 仍为 350V**（`main.h:93`）
   → 264V 输入时预充峰值 ≈373V 会越过 350V，PFC 未起环即放行 LLC。
   台架现象：`pfc_state` 仍为 `RELAY_ON`(1) 时 `state` 已跳 `CC`(3)。
   建议改 `(VBUS_TARGET_V * 0.98f)` = 372.4V。

2. **`pfc_enable` 无 AC 上电宽限**（补丁 D 未打）
   → AC RMS 是 200ms/1000 样本整周期窗口，上电后第一个有效 RMS 需 200ms。
   若上电后立刻 `START`，`ac_vol_v = 0` 会触发 `FAULT_AC_INPUT_RANGE` → **又踩 FAULT 死锁**。
   **规避**：等串口打印出正常的 `ac=xxxV` 值再敲 `START`。

## 16.2 去掉 `!protect_fault_latched()` 是否安全？—— 是

`g_fault` 与 `s_fault_latched` 在 `protect.c` 中**始终成对写入**：

| 位置 | 动作 |
|---|---|
| `protect.c:73-74` | `s_fault_latched = false;` + `g_fault = FAULT_NONE;` |
| `protect.c:80-81` | `s_fault_latched = true;` + `g_fault = f;` |

不存在只写其一而不写另一的路径。因此

```
g_fault == FAULT_NONE  ⟺  s_fault_latched == false
```

两个条件是**等价**的，删掉一个不改变语义。

> **健壮性提示（非缺陷）**：这个等价关系是隐式约定。若将来有人在 `protect.c` 之外单独写 `g_fault`（例如直接 `g_fault = FAULT_NONE;` 而不清锁存），等价性会被打破，此处的判断就会失准。建议在 `protect.c` 的两处写入点加注释声明该不变式。

## 16.3 会不会被"自动"满足而产生误退出？—— 不会

对**所有**进入 FAULT 的路径做了穷举（`grep -an` 全工程）：

**进入路径（仅 2 条）**：

| # | 路径 | 是否设置 `g_fault ≠ NONE` |
|---|---|---|
| 1 | `protect_set_fault()` → `power_supervisor_enter_fault()` → `enter_state(MAIN_STEP_FAULT)` | ✅ 是（`protect.c:81`） |
| 2 | `main.c:288` 直接赋值 `g_charger_state = MAIN_STEP_FAULT` | ✅ 是（`main.c:289` `g_fault = FAULT_HARDWARE_PRO`），且紧随 `while(1){__NOP();}`，tick 不会运行 |

**`protect_set_fault()` 的全部 10 处调用，实参均为非 NONE 故障码**：

```

llc_control.c:351  FAULT_CHARGE_TIMEOUT      (CC 超时)
llc_control.c:367  FAULT_OUTPUT_START_TIMEOUT

## 16.4 使能标志的时序是否阻挡了自动退出？—— 是

`protect_set_fault()` **不清 `s_enable_requested`**：

```c
void protect_set_fault(fault_type_t f)
{
    s_fault_latched = true;
    g_fault = f;
		power_supervisor_enter_fault();   /* enter_state(FAULT) → outputs_force_off()
		                                   * 但不动 s_enable_requested */
}
```

而 `enter_state(MAIN_STEP_FAULT)` 的动作（`llc_control.c:189-195`）只有：

```c
case MAIN_STEP_FAULT:
{
    outputs_force_off();              /* llc_disable + PWM safe + OUT_RELAY off + pfc_disable */
    gpio_bit_set(LED_RED_PORT, LED_RED_PIN);
    gpio_bit_reset(LED_GREEN_PORT, LED_GREEN_PIN);
    break;
}
```

**不含 `s_enable_requested = false`。** 因此故降发生时 `s_enable_requested` 仍为 `true`，新出口的第一个条件不成立 → **必须操作员显式 `STOP`**。

两条命令的时间线（缺一不可）：

```
故障发生     g_fault=FAULT_CHARGE_TIMEOUT, s_enable_requested=true   → 条件不成立，留在 FAULT
STOP         s_enable_requested=false,      g_fault 仍 ≠ NONE        → 条件仍不成立
CLEAR        g_fault=FAULT_NONE,            s_fault_latched=false     → 下一 tick 满足 → 回 STANDBY ✓
```

## 16.5 修复后的完整台架路径（可迭代，无需掉电）

```
上电          g_fault=NONE, state=STANDBY
SET 72 2      → OK SET       （apply_references() 立即下发 PWM）
START         → OK START     （s_enable_requested=true）
  STANDBY     → BENCH 分支 if(s_enable_requested) → PRECHARGE（pfc_enable 在此）
  PRECHARGE   → pfc_is_ready()（PFC RUN + AC∈[165,264] + bus∈[350,420]）→ CC
  CC          → apply_references() + llc_enable() + outputs_on()（合 OUT_RELAY）
  CV          → 3s 后 CHARGE_CV_TIMEOUT → FAULT
FAULT         → outputs_force_off()；!s_enable_requested 为假 → 留在 FAULT
STOP          → OK STOP
CLEAR         → OK CLEAR     → 下一 tick 自动回 STANDBY ✓
  ← 可重新 SET / START，不需掉电 ✓
```

**死锁已解除。** 剩下的限制是 CV 态只有 3s 窗口（`CHARGE_CV_TIMEOUT_MS`，调试值），若需长时间观察 CV，把该宏调大即可。
