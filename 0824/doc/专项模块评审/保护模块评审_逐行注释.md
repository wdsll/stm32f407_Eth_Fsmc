## 〇、一句话结论

模块结构与去抖正确、fail-safe 断电链路通。但 **`protect_fault_active_hw()` 被临时硬编码为恒假**——硬件故障检测层整体下线，protect_tick 的 LLC_CHECK 检查、CLEAR 的"硬件未解除拒绝清"守卫、启动自检的硬件故障拦截、串口 START 的三重门，全部随之失效或退化。若这是联调期规避误报的临时措施，必须挂"量产前恢复"的牌；若 D 触发器硬件本身没焊/没验证，要写进硬件待办。

## 二、专节：`protect_fault_active_hw()` 硬编码关闭的全链路影响

```c
bool protect_fault_active_hw(void)
{
    #if 1
        return false;          /* ← 硬件故障检测整体下线 */
    #else
        return (gpio_input_bit_get(LLC_FAULT_CHECK_PORT, LLC_FAULT_CHECK_PIN) == 1U);
    #endif
}
```

**五处连锁（v3 逐一核实）：**

| # | 受影响点 | 现状 |
|---|---|---|
| 1 | `protect_tick_1khz:97` LLC_CHECK 轮询 | 死代码，硬件锁存故障无法被感知 |
| 2 | `protect_clear_fault:72` "硬件未解除拒绝清" | 守卫恒真 → 串口 CLEAR 无条件清软锁存+故障码 |
| 3 | `main.c protect_startup_check:181/189` | 两处 active_hw 检查恒假 → 上电自检不再拦截硬件故障 |
| 4 | `serial_console.c:212` START 三重门 | 退化两重（故障态+锁存），"硬件故障未解除拒启动"失效 |
| 5 | `llc_control.c:287` FAULT 恢复条件 `!protect_fault_active_hw()` | 恒真项，条件实际=`!en && !latched`（见 llc_control 评审 v3 B2 专节） |

**处置建议（按意图二选一）：**
- **A. 联调临时措施（误报/引脚悬空）**：在 `#if 1` 上方加显式注释 `/* TODO(量产前): restore hardware fault polling after D-FF bench validation */`，并同步把上面 5 处"恢复时必须联动"的点写进本文档检查清单——尤其串口 CLEAR 的拒绝分支（serial_console.c:236-239 被注释）与 START 三重门。
- **B. 硬件本就未焊/未接**：把"LLC_FAULT_CHECK D 触发器焊接/验证"写进硬件待办；`#else` 分支恢复前先实测极性（注释"低=故障"与代码 `==1U` 判高矛盾，二者必有一错）。

## 三、FAULT 恢复链路（v3 重述，承接状态机 v2 复审）

当前完整恢复路径（实测语义）：
```
故障触发 → protect_set_fault: latched=true, g_fault=f, enter_state(FAULT), outputs_force_off
    ↓（FAULT 态每 tick：protect_tick 早退 + supervisor 顶部 outputs_force_off）
串口 STOP  → s_enable_requested=false
串口 CLEAR → protect_clear_fault: 脉冲清 D 触发器 + (守卫恒真)清 latched + g_fault=NONE
    ↓ 下一 1kHz tick
supervisor_tick FAULT 分支：!en && !latched 满足 → g_fault=NONE, enter_state(STANDBY) ✓
```
- 链路**通**，无死锁；但**不存在无人干预的自恢复**（latched 只能被 CLEAR 清）——这是"人工确认"语义，当前状态合理（v2 状态机复审结论）。
- 硬件侧：CLEAR 的 10ms 脉冲确实会去清 D 触发器（HARD_FAULT_CLR 拉高）——即使 active_hw 轮询关着，外部锁存仍会被真清掉。若硬件故障源（HARD_PRO）仍有效，D 触发器会重新锁存，但 MCU 已不再轮询感知——**功率级已被 outputs_force_off 断电，安全风险可控；但"故障仍在却显示 NONE"的误导是真实的**。

## 四、遗留问题清单（v3）

### P0（CPU/看门狗级兜底，无人值守前必须）
1. **CPU 异常不关功率**（`gd32f30x_it.c`：HardFault 等 handler 全 `while(1)` 且不碰 GPIO）：补 `fault_safe_off()`（handler 内直接 reset PFC_RELAY/LLC_EN/OUT_RELAY，用 `llc_disable()` 语义即拉高）→ **未落实**。
2. **IWDG 未启用**：`fwdgt_config(~1.5s, FWDGT_PSC_DIV64)` + `fwdgt_enable()`，1kHz 主循环末尾 reload → **未落实**。
3. **(v3 新增归入 P0) active_hw 恢复计划**：见第二节处置 A/B，写明恢复时间点与联动清单 → **待用户拍板**。

### P1（安全相关）
4. **① 硬件直断路径待核对原理图**：LLC_FAULT_CHECK/HARD_PRO 是否同时接 NCP4390 BKIN 或硬件门控 LLC_EN？若停功率完全依赖 MCU 软件，与 P0-1/2 叠加成"MCU 失声=三路全失守" → **未核对**。
5. **② 断电无缓冲时序（B1）**：`outputs_force_off` 同 tick 齐断（详 llc_control 评审补丁 A）→ **未落实（最高剩余风险）**。
6. **③ (v3 新增) `:47` IPD/上拉矛盾 + `#else` 分支极性矛盾**：恢复 active_hw 前必须先解这两个矛盾（实测 D 触发器输出类型与极性）→ **新增**。

### P2
7. **过温保护恢复前置**：四处同步启用（见 :114-118 注释）→ **维持关闭（符合指令）**。
8. **OCP 兜底**：`isense_raw >= 4000` 饱和即 FAULT_OCP（贴边 24.8A 量程）→ **新增建议**。
9. **ADC 失效时的保护真空**：protect_tick 直接信 `g_adc_multi`，未查采样有效性；初版可接受，记录。

### P3
10. `:88` extern 冗余可删。
11. llc_control.c `outputs_force_off` 函数头旧注释"C5 未复位"过时（已在 llc_control 评审 v3 清单）。

## 五、亮点（v3 保留）

- ✅ `protect_set_fault` 即时断三路再锁存，fail-safe 链路完整（LLC_EN 极性已随新封装更新为低有效拉高）。
- ✅ FAULT 态早退 + 去抖复位，防重复触发与跨状态残留。
- ✅ CLEAR 脉冲时序（10ms+5ms）匹配 D 触发器要求，任务上下文阻塞可接受。
- ✅ OVP/OCP 用 condition_held 30ms 去抖，与状态机共用同一去抖组件。
- ✅ 上电 `protect_startup_check`（先查硬件故障→再清锁存）顺序正确——虽然 active_hw 恒假后第一步失效，结构本身是对的。
