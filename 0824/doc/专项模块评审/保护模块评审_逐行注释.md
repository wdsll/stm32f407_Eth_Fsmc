# 保护模块评审报告（逐行注释）

> 更新时间：2026-08-24（对齐 0824 工程 08-20 之后代码状态）
> 相对上一版的变化：① 去抖逻辑重构为独立 `condition_held.h`（结构体 `condition_qualification_t`）；② `main.c` 新增 `protect_startup_check()` 与 preflight 自检，部分落实了"上电清锁存"；③ CPU 异常关功率、IWDG、断电缓冲时序等安全建议**仍未落实**（见文末状态表）。

评审对象（0824 工程，GD32F303RE）：
- `HW/src/protect.c` + `HW/include/protect.h` —— 故障保护（硬件锁存轮询 + 软件 OVP/OCP/过温）
- 关键依赖：`llc_control.c` 的 `power_supervisor_enter_fault()` → `enter_state(MAIN_STEP_FAULT)` → `outputs_force_off()`；`main.c` 的 `monitor_protect_tick_1khz()`（1kHz）调用 `protect_tick_1khz()`；`main.c` 的 `protect_startup_check()`（上电自检）。

接线/调用核对（已确认）：
- `main.c:147` 每 1kHz 调 `protect_tick_1khz()`，顺序在 ADC 采样(144)、PFC(150)、功率状态机(153) 之前——**保护优先级最高，正确**。
- 故障触发链：`protect_set_fault()` → `power_supervisor_enter_fault()` → `enter_state(FAULT)` → `outputs_force_off()`（关 LLC_EN / 复位 CV·CC PWM 占空比 / 断 OUT_RELAY / `pfc_disable()`）。软件故障确实会断功率，链路通。
- `protect_clear_fault()` 由串口 CLEAR 命令调用（任务上下文），内部用 `delay_ms` 阻塞 10+5=15ms。
- **新增**：`main.c:175` `protect_startup_check()` 在 preflight 阶段调用——硬件故障在则启动失败；软件锁存则尝试清锁存。**这比旧版"init 末尾补 CLR 脉冲"更合理**，已部分解决旧 P2-④。

总体评价：**模块结构正确、去抖合理、硬件锁存设计好、清除逻辑安全**。初版软硬联调可用。仍存在两个必须点名的安全点：(1) 硬件故障信号「只给 MCU 轮询、无硬件直断」——MCU 死机时功率级继续运行（见 P0/P1）；(2) `outputs_force_off()` 三路同 tick 齐断、无缓冲时序，继电器有拉弧/粘连风险（B1）。这两点与"CPU 异常只死循环不关功率"互相放大。

## 五、安全体系缺口（新增，关联之前「CPU 异常只死循环」评审）

| 位置 | 现状 | 评审注释 |
|---|---|---|
| `gd32f30x_it.c:21-75` | NMI 空；HardFault/MemManage/BusFault/UsageFault 全 `while(1)` | **P0**：异常只死循环，不碰任何 GPIO。一旦发生 CPU 异常，功率级 GPIO 保持故障前状态继续运行，软件监控全停。必须补 `fault_safe_off()`：在 handler 内直接 `gpio_bit_reset` 关 PFC_RELAY/LLC_EN/OUT_RELAY（不依赖其他状态），然后 `while(1)` 等 IWDG 复位。**当前状态：未落实**。 |
| 全工程 | 无 `fwdgt_config/enable/reload`，无 WWDG | **P0**：独立看门狗完全未启用。建议 `main.c` 初始化后 `fwdgt_config(936, FWDGT_PSC_DIV64)`（~1.5s，基于 IRC40K 独立时钟）+ `fwdgt_enable()`；在 1kHz 监控主循环末尾 `fwdgt_counter_reload()`。**当前状态：未落实**。 |
| 两处叠加 | — | 上表 P0 与保护模块「①硬件无直断」「B1 齐断」叠加：MCU 一旦失声，三个层面都失去停功率能力。建议至少补①异常处理器关功率 + ②IWDG 兜底复位。 |

`fault_safe_off()` 参考实现（handler 里写 GPIO 不依赖主循环，安全）：
```c
#include "hw_port.h"   // 含 PFC_RELAY_*/LLC_EN_*/OUT_RELAY_* 宏
static void fault_safe_off(void) {
    gpio_bit_reset(PFC_RELAY_PORT,  PFC_RELAY_PIN);
    gpio_bit_reset(LLC_EN_PORT,     LLC_EN_PIN);
    gpio_bit_reset(OUT_RELAY_PORT,  OUT_RELAY_PIN);
    /* 不要在此脉冲清 HARD_FAULT_CLR，保持硬件锁存断电 */
}
void HardFault_Handler(void)   { fault_safe_off(); while (1) {} }
void MemManage_Handler(void)    { fault_safe_off(); while (1) {} }
void BusFault_Handler(void)     { fault_safe_off(); while (1) {} }
void UsageFault_Handler(void)   { fault_safe_off(); while (1) {} }
void NMI_Handler(void)          { fault_safe_off(); while (1) {} }
```

## 六、问题清单（按严重度 + 落实状态）

### P0（建议第一版就做，CPU/看门狗级兜底）
1. **CPU 异常不关功率**（`gd32f30x_it.c`）：补 `fault_safe_off()`，异常时强制断 PFC_RELAY/LLC_EN/OUT_RELAY。→ **未落实**。
2. **独立看门狗 IWDG 未启用**：`main.c` 加 `fwdgt_config + enable`，1kHz 主循环末尾 `fwdgt_counter_reload()`。→ **未落实**。

### P1（安全相关，初版处理/至少核对原理图）
3. **① 硬件故障是否「仅 MCU 轮询、无硬件直断」**（`protect.h:1-3`）：
   - 现状：NCP4390 的 HARD_PRO 经 D 触发器 → `LLC_FAULT_CHECK` 给 MCU 轮询；MCU 再软件拉低 `LLC_EN` 停 LLC。停功率完全依赖 MCU 软件，且 **MCU 死机时功率级继续运行**（与 P0 叠加）。
   - 必须核对原理图：`LLC_FAULT_CHECK`/`HARD_PRO` 是否还直连 NCP4390 的 **BKIN/硬件关断脚**，或经硬件门控直接拉 `LLC_EN`？若没有硬件直断路径，是显著安全隐患。
   - 建议：把故障信号（或 D 触发器输出）同时接到 LLC 控制器的硬件 disable/BKIN（或逻辑门在故障态强制 `LLC_EN=0`），让停功率**不依赖 MCU**。→ **需核对原理图（未落实）**。
4. **② 断电无缓冲时序（B1）**（`outputs_force_off` / llc_control.c:110-117）：改为「先关 LLC → 泄放 → 再断继电器」。→ **未落实**。

### P2（建议初版内修/核对的边界项）
5. **③ 过温保护恢复前置条件**：重新启用 protect.c:110-114 前，确认 `g_adc_multi.t_*` 已被 `adc_dma` 实际填充，否则温度保护静默失效。→ **保持关闭，待恢复（符合指令）**。
6. **④ 上电清除锁存**：已通过 `main.c:175` `protect_startup_check()` 部分落实（上电尝试清锁存 + 硬件故障在则停）。比旧方案更稳。→ **已部分落实（✓）**。
7. **② OVP 阈值调参**：`VOUT_OVP_V=64V` 对 58.4V 满电约 10% 裕量，可接受；想更紧可下压到 ~60–62V。→ **未改，按电池规格定**。
8. **ADC 失效时的保护真空**：`protect_tick` 直接信 `g_adc_multi.vout/iout`，未检查 `adc_valid()`（main.c:167 有该检查但未在此用）。ADC 卡极值时可能误判。初版可暂不加。

### P3（代码整洁）

10. **`outputs_force_off` 旧注释「C5 未复位 CV/CC PWM」过时**（llc_control.c:108）：代码 113-114 已复位，删该句。→ **未落实**。
