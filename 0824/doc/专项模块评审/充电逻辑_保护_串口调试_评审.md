# 充电逻辑 / 保护 / 串口调试 专项评审

> 范围: 充电逻辑（PFC 子状态机 + PWM 设定值生成 + ADC 采样）、硬件/软件保护（protect.c/.h）、新增串口调试（debug_printf + serial_console）
> 评审日期: 2026-08-14
> 已读文件: `pfc_control.c/.h` `pwm_llc.c/.h` `adc_dma.c/.h` `protect.c/.h` `main.c/.h` `debug_printf.c/.h` `serial_console.c/.h`
> 说明: 本文"充电状态机 llc_control"部分沿用此前《llc_control代码评审》，此处只补充新发现的联动问题；重点在 PFC、PWM、保护、串口三块。

---

## 〇、整体结论（先看这里）

架构与 fail-safe 思路是对的（保护即时断三路、非阻塞串口、ADC 用 DMA+FTF 同步、不补跑丢失节拍）。但当前版本在**你关心的三块**里各有阻断级/严重问题：

- **充电逻辑**：PFC 子状态机缺恢复路径；PWM 软启动宏定义了却从未调用（阶跃下发基准，有浪涌风险）；**ADC 根本不扫温度/风扇通道**，导致过温保护与降额在物理上不可能生效。
- **保护**：软件 OCP 判据 30A 超过 ADC 满量程（约 24.8A），**后备过流保护是死代码**；过温 4 路整段注释；**母线过压（VBUS_OVP）缺失**；最致命的是**故障恢复路径断裂——CLEAR 只清硬件锁存，不把 `g_charger_state` 踢出 FAULT**，系统永久锁死。
- **串口调试（新加）**：`SET` 命令用了 `scanf` 而非 `sscanf`，**命令完全失效**；`START` 在 UART 联调下会因 CAN 超时保护**立刻锁 FAULT**；CLEAR 同样受恢复断裂影响，清完也回不到待机。

> 这三块问题相互耦合：串口是"首次软硬联调"入口，但它一 START 就踩 CAN 超时故障、一 CLEAR 也救不回来——**当前的串口联调通道实际上是走不通的**。

## 一、充电逻辑

### 1.1 PFC 子状态机（pfc_control.c）

状态：`OFF → RELAY_ON → RUN → FAULT`。驱动：`pfc_tick_1khz()`（1kHz）。

| 位置 | 行为 | 评价 |
|---|---|---|
| `:34-42` `pfc_enable` | 仅 OFF 态响应，闭合 PFC 继电器，进 RELAY_ON | OK |
| `:56-62` RELAY_ON | 等 100ms（NCP1654 软启 ~50ms）后进 RUN | OK，门限合理 |
| `:64-75` RUN | `bus_vol_v < VBUS_TARGET*0.8`(=304V) 持续 200ms → `FAULT_BUS_UVP` | 去抖 OK，但**只有欠压、无过压** |
| `:77-79` PFC_FAULT | 每 tick `pfc_disable()` | ⚠ **无恢复**，永远卡在 FAULT |
| `:85-89` `pfc_is_ready` | `state==RUN && bus_vol_v >= LLC_ENTRY_V`(360V) | 与 llc PRECHARGE 共同决定进 CC |

**问题 P1 — PFC 进入 FAULT 后无恢复路径（严重）**
`pfc_tick` 进 `PFC_FAULT` 后只反复 `pfc_disable()`。没有任何代码把 `s_pfc_state` 复位回 `PFC_STATE_OFF`/`RELAY_ON`。恢复只能依赖上层的 `g_charger_state` 退出 FAULT（见保护 2.4）。两者都没做 → PFC 永久失能，除非断电。

**问题 P2 — 母线过压（VBUS_OVP）完全缺失（严重）**
`protect.c` 里只查 `bus_vol < 304V`（欠压，且在 pfc_control 内）。NCP1654 是模拟控制器，一旦反馈异常母线可能冲高，没有上限保护。建议加 `FAULT_BUS_OVP`（如 `bus_vol_v > 430V`）并在 `protect_tick_1khz` 中轮询。

**问题 P3 — `pfc_is_ready` 与保护门限之间存在死区（中等）**
`pfc_is_ready` 要求母线 ≥360V，但 `FAULT_BUS_UVP` 要到 <304V 才报。母线停在 304~360V 之间时：PFC 是 RUN（不报故障）、但 `pfc_is_ready()` 恒假 → llc 的 PRECHARGE **永久等不到进 CC**（与 llc 评审 A1 叠加）。正常稳态母线 ~380V 不受影响，但若 PFC 输出偏弱会卡死。

### 1.2 PWM 设定值生成（pwm_llc.c）

CV_PWM=TIMER0(CH0,PA8)、CC_PWM=TIMER1(CH0,PA0)，把"占空比"经板级 RC 滤波变成模拟 IC 的电压/电流基准。

**亮点**：时钟处理正确——CV 用 `CK_APB2`（TIMER0 在 APB2）、CC 用 `timer1_clk_hz()`（TIMER1 在 APB1，且正确应用了 APB1PSC 的 ×2 规则，`:29-33`）。占空比均做了 `f_clampf` 限幅，shadow 更新正确。

**问题 P4 — 软启动宏定义了却从未调用（严重，沿用此前 M2）**
`main.h:178-185` 定义了 `LLC_SOFTSTART_*`（`CV 5%→50%`、`CC 2%→30%`），但 `cv_pwm_set_duty`/`cc_pwm_set_duty`（`:81-87`/`:128-134`）都是**瞬时置占空比**。当串口 `SET` 或 `START` 下发基准时，PWM 直接阶跃到目标占空比 → LLC 输出电压/电流基准阶跃 → 有冲击/过冲风险。模拟 IC 闭环会跟随，但大步进仍不可取。建议在 `set_duty` 路径或 supervisor 里加斜率限制，启用已定义好的软启动宏。

### 1.3 充电状态机联动（llc_control，补遗）

- 此前的 A1（PRECHARGE 无超时）、B2（FAULT 不可恢复）在新增串口后仍成立，且被串口 CLEAR 暴露（见 3.3）。
- `power_supervisor_set_references` 立即 `apply_references()`（基准阶跃），与 P4 同源。

### 1.4 ADC 采样通道（adc_dma.c）—— 温度/风扇根本没扫

`adc_dma.c:37-40` 扫描序列只有 5 路：`AC_VOL, BUS_VOL, VOUT, I_SENSE, VBT`。
`main.h:123-149` 明明定义了 4 路温度（`T_SENSE_CASE/PFC_MOS/LLC_MOS/TR`）和风扇电流（`FAN_CS`），**但都不在扫描列表里**，且 `ADC_CHANNEL_QTY=5`（`main.h:151`）也只够这 5 路。

后果：
- `g_adc_multi.t_pfc_c` 等温度字段**永远是 0（未初始化）**；
- `ntc_raw_to_temp_c()` 整个被 `#if 0`（`:168-188`）；
- protect.c 里 4 路过温整段注释（`:114-117`）。

→ **过温保护在物理上不可能工作**，降额宏 `TEMP_DERATING_START_C/FULL_C`（`main.h:75-76`）从未被引用。对一个 1.5kW 功率产品，这是关键安全缺口。必须：把 4 路 NTC + 风扇电流加入 ADC 扫描 → 实现 NTC 换算 → 解注释 protect 过温分支 → 加降额。

## 二、保护部分（protect.c / main.h）

### 2.1 软件 OCP 失效：30A 超过 ADC 满量程（严重）🔴

`main.h:91` `IOUT_OCP_A = 30.0f`；`protect.c:108-111` 判据 `g_adc_multi.iout_a > 30`。

电流换算（`adc_dma.c:159-167`）：`iout = (Vadc - 1.65) / (0.00333 × 20)`。
- 0A → 1.65V；20A(额定) → 2.98V；**24.8A → 3.30V（触顶饱和）**；30A → 理论 3.65V 但被供电轨钳到 3.3V。
- 即 `iout_a` 最大值约 **24.8A**，永远到不了 30A → `>30` **恒假，OCP 是死代码**。

更严重：额定 20A 已用到量程的 90%，**模拟硬件限流必须动作在 24.8A 之前**，否则 MCU 侧既看不到、也保护不了。

**修复**：OCP 改到可检测区间，例如 `IOUT_OCP_A = 22~24A`；并建议增加"ADC 饱和即判过流"（raw 接近 4095 直接 FAULT_OCP），作为对模拟限流的兜底。

### 2.2 过温保护完全缺失（严重）🔴

`protect.c:114-117` 4 路过温整段 `//` 注释，且无温度采样（见 1.4）。**任何功率器件过热都不会触发保护**。这是量产不可接受项，优先级与 2.1 同级。

### 2.3 母线过压缺失（严重）

同 P2：仅 `BUS_UVP`（欠压）在 pfc_control 内，`protect.c` 无 `BUS_OVP`。建议补 `FAULT_BUS_OVP` 轮询。

### 2.4 故障恢复路径断裂（最致命）🔴

这是把三个模块串起来的核心缺陷：

1. `protect_set_fault()`（`protect.c:70-79`）在锁存时把 `g_charger_state = MAIN_STEP_FAULT`。
2. 运行时清故障只有两条路：
   - `protect_clear_fault_async()`（`:50-57`）：拉高 `HARD_FAULT_CLR` 脉冲，由 `protect_tick_1khz`（`:87-91`）在 10ms 后拉低，并**只把 `s_fault_latched=false`**，**不碰 `g_charger_state`**；
   - `protect_clear_fault()`（`:61-68`，仅启动自检用）：同样不复位 `g_charger_state`。
3. `llc_control.c:141` `if (g_charger_state == MAIN_STEP_FAULT) { outputs_off(); return; }` —— 只要 `g_charger_state` 还是 FAULT，`power_supervisor_tick` 每 tick 直接 return，**没有任何分支把它转回 STANDBY**。
4. `pfc_tick` 同理卡在 `PFC_FAULT`（见 P1）。

**结果**：无论硬件锁存清没清、`s_fault_latched` 是否为假，`g_charger_state` 永远停留在 `MAIN_STEP_FAULT` → 充电状态机永久锁死。串口 `CLEAR` 命令（见 3.3）只清了硬件锁存，对软件状态无能为力。

**修复（必须有）**：在 `power_supervisor_tick_1khz` 的 FAULT 分支里，当 `!protect_fault_latched() && !protect_fault_active_hw()` 时，先执行安全断电时序（见此前 B1）再 `enter_state(MAIN_STEP_STANDBY)`。即把"故障已清除且无硬件故障"作为退出 FAULT 的条件。

### 2.5 OVP 阈值偏高（中等）

`VOUT_OVP_V = 80V`（`main.h:89`）。对默认 58V(12S/14S) 目标，80V 意味着输出冲到约 1.38× 才动作，对电池包偏宽松。建议按电池化学上限设更紧的 OVP（如 63~65V），80V 仅作绝对硬件极限。

### 2.6 亮点（保护）

- `protect_set_fault()` **即时断三路**（OUT_RELAY / LLC_EN / PFC_RELAY）再锁存，fail-safe 正确（`:73-76`）。
- `protect_tick` 进 FAULT 后 `return` 停止轮询，避免反复触发，思路对。
- 启动自检 `protect_startup_check()` 先查硬件锁存再清，顺序正确。

## 三、串口调试（新增，debug_printf + serial_console）

> 入口：`main.c` 调用 `debug_printf_init()` + `serial_console_init()`；`while(1)` 里 `serial_console_task()` + `debug_tx_task()`。CAN 在首版联调**故意不初始化**（`main.c:256-257` 注释掉 `can_comm_init`）。

### 3.1 `SET` 命令用了 `scanf` 而非 `sscanf` → 命令完全失效（阻断）🔴

`serial_console.c:60`：
```c
else if(scanf(line,"SET %f %f",&voltage_v,&current_a) == 2)
```
标准 C 里 `scanf(const char *fmt, ...)` 的**第一个参数是格式串、从 stdin 读取**。这里把 `line` 当格式串、把 `"SET %f %f"` 当普通参数 —— 它**根本不会解析 `line` 里的内容**，而是尝试从 stdin（嵌入式无）读，行为未定义，实际返回 0/EOF。

后果：`SET 58 20` 这类命令永远进不到这个分支，最终落到 `else` → 打印 `ERR unknow command`。**串口联调最核心的"设电压电流"功能不可用**。

**修复**：改为 `sscanf(line, "SET %f %f", &voltage_v, &current_a)`。

### 3.2 `START` 在 UART 联调下立刻触发 CAN 超时故障（阻断）🔴

`llc_control.c:138-140`：
```c
if (s_enable_requested && can_comm_timeout()) {
    protect_set_fault(FAULT_CAN_TIMEOUT);
}
```
UART 联调时 CAN **未初始化**，`can_comm_timeout()` 的"上次收到帧时间戳"为 0/从未更新 → `elapsed_reached(0, ...)` 立刻为真 → 一旦串口 `START` 置 `s_enable_requested=true`，**下一个 1kHz tick 立即报 `FAULT_CAN_TIMEOUT`**，充电状态机直接进 FAULT。

**后果**：串口 `START` 充电在首版联调里**必现 FAULT**，联调通道走不通。

**修复**：CAN 超时故障必须门控——仅当"CAN 已初始化 / 处于 CAN 模式"时才使能该判据。例如加 `g_can_active` 标志（仅 `can_comm_init` 成功后置位），或在 `COMMISSIONING_USE_UART` 宏下跳过该分支。

### 3.3 串口 `CLEAR` 救不回系统（严重，同源 2.4）

`serial_console.c:92-107` `CLEAR` 调 `protect_clear_fault_async()`，清了硬件锁存与 `s_fault_latched`。但如前 2.4，`g_charger_state` 仍是 `MAIN_STEP_FAULT`，`llc_control` 永久 return。所以即便硬件故障已消失，`CLEAR` 之后系统依旧锁死，必须断电。

**修复**：与 2.4 合并解决——在 FAULT 退出条件里加"故障已清"分支。

### 3.4 其它（次要）

- `serial_console.c:110` `ERR unknow command` 拼写应为 `unknown`。
- 看门狗逻辑（`:143-147`）：`enable` 且 5s 无命令 → 自动 `STOP`，设计合理；但注意 `STATUS` 自动打印（每 500ms）**不刷新** `s_last_command_ms`，所以"只看不敲"5s 也会自动停——这是预期的"心跳"语义，OK。
- `debug_printf` 当前仅被主循环调用，**未在任何 ISR 中使用**，环形缓冲无临界区保护是安全的；但属脆弱设计——后续若在 ISR 里加 `debug_printf` 会破坏环形缓冲。建议注释声明"禁止 ISR 调用"或加简单的开关中断保护。
- 无鉴权：联调台架上可接受，但 `START` 可带任意设定值启动充电，量产固件务必移除该控制台（或加使能宏彻底编译掉）。
- `debug_printf` 局部 `line[256]` + 环形 `s_tx_buf[1024]` 均做了长度保护，溢出风险低。

### 3.5 亮点（串口）

- 非阻塞发送（环形缓冲 + `debug_tx_task` 在主循环排水）、接收逐字符解析，**不阻塞 1kHz 控制环**。
- 安全意图到位：SET/CLEAR 要求先 STOP；START 校验参考值已设；5s 心跳看门狗自动停车。

## 五、修复优先级建议

```
P0（联调通道能否跑通，且都是阻断/致命）：
  1. 3.1  scanf → sscanf              —— 否则 SET 完全无效
  2. 3.2  CAN 超时故障门控(g_can_active) —— 否则 START 立即 FAULT
  3. 2.4  FAULT 退出条件(故障清+无硬件故障→STANDBY) —— 否则 CLEAR/任何恢复都无效
  4. 2.1  OCP 改到 ≤24A + 饱和检测     —— 否则后备过流保护是死代码
  5. T1+2.2  ADC 加温度通道 + 解注释过温 + NTC 换算 + 降额 —— 否则无过温保护

P1（安全/稳定）：
  6. P2/P3  补 VBUS_OVP + 收窄 pfc_is_ready 与 BUS_UVP 死区
  7. P1     PFC FAULT 恢复路径
  8. P4     启用软启动/斜率限制，消除基准阶跃
  9. 2.5    OVP 阈值按电池化学收紧

P2（清理）：
 10. 3.4   拼写/ISR 调用约束/量产移除控制台
```

> 其中 3.1、3.2、2.4 三者不修，**首次软硬联调根本无法进行**——建议优先于一切。
