# 0824 OBC 固件代码评审报告

> 项目: `offline OBC/0824` — 1.5kW OBC (GD32F303RE)  
> 版本: main.h 标注 v0.1.0  
> 评审日期: 2026-08-11  
> 评审人: 小姜 (WorkBuddy)

---

## 〇、总体结论

**架构方向正确，安全关键实现缺失严重。当前版本不能正常工作，也不能用于量产。**

- 节拍调度（中断置标志 + 主循环原子取走）、故障即时断电（fail-safe）、状态机骨架——这些设计是**用心且清晰**的。
- 但存在 **2 个阻断级 bug**（CAN 帧格式错误导致永远收不到使能命令；充电超时误用 8s/3s 调试值导致 8 秒即锁死）+ **3 个关键安全缺口**（过温保护全注释、软件 OCP 阈值超量程恒假、无任何温度降额/看门狗/故障恢复）。
- 优先修复顺序：**先让系统能跑起来（C1、C2）→ 补齐保护（C3、C4、M1、M2、M3）→ 清理死代码与标定（Minor）**。

严重级定义:
- 🔴 **阻断级(Blocker)**: 系统无法启动/无法完成基本功能
- 🟠 **关键(Critical)**: 保护失效，有安全隐患
- 🟡 **主要(Major)**: 设计缺陷，影响可靠性/可维护性
- 🟢 **次要(Minor)**: 代码质量/潜在隐患

## 一、阻断级问题 (Blocker)

### 🔴 C1 — CAN 帧格式与 ID 不匹配，BMS 命令永远收不到

| 项 | 内容 |
|----|------|
| 位置 | `can_comm.h:6-8` (ID 定义)、`can_comm.c:61,83,107-108` (收发) |
| 现象 | `CAN_ID_CHARGER_STATUS=0x1801`、`CAN_ID_BMS_CONTROL=0x1802` 是 **29 位 J1939 地址**，但收发均用 `CAN_FF_STANDARD`（11 位，最大 0x7FF=2047）。 |

详细分析:
- 过滤器: `filter_list_high = (0x1802 << 5) & 0xFFFF = 0x0040`，按 11 位标准帧解析实际只匹配 **标准 ID=0x02** 的帧（头注释自相矛盾地写"J1939/标准帧"）。
- 软件判据: `can_comm.c:83` `if (rx_msg.rx_sfid == CAN_ID_BMS_CONTROL)` —— `rx_sfid` 是 11 位字段，对标准帧永远不可能是 0x1802，**恒为假**。
- 后果: BMS 控制帧要么被硬件过滤器丢弃，要么通过过滤器后被软件判据拒绝，**`s_enable_requested` 永远为 false，充电机永久停在 STANDBY，无法启动充电。**

**修复建议（二选一）:**
1. 若用**标准帧**: 把三个 ID 改为 ≤ 0x7FF（如 0x100/0x101/0x102），保持 `CAN_FF_STANDARD`。
2. 若用 **J1939 扩展帧**: `tx_ff = CAN_FF_EXTENDED`；接收改用 `rx_efid` 判据；过滤器按 29 位配置（EID 占 filter 高 29 位）；发送填 `tx_efid`。同时建议给 `can_rx_data_t`/`can_tx_data_t` 补上协议版本/长度校验。

---

### 🔴 C2 — 充电超时误用 8s/3s 调试值

| 项 | 内容 |
|----|------|
| 位置 | `main.h:100-106` |
| 现象 | `#if test_mode` 中的 `test_mode` **全工程从未定义**，未定义标识符在 `#if` 中视为 0，因此走 `#else` 分支： |

```c
#if test_mode          // test_mode 未定义 → 视为 0 → 走 #else
#define CHARGE_CC_TIMEOUT_MS  (8U*60U*60U*1000U)   // 8 小时 (test_mode 时才用)
#define CHARGE_CV_TIMEOUT_MS  (3U*60U*60U*1000U)   // 3 小时
#else
#define CHARGE_CC_TIMEOUT_MS  (8U*1000U)           // ← 实际生效: 8 秒 !!
#define CHARGE_CV_TIMEOUT_MS  (3U*1000U)           // ← 实际生效: 3 秒 !!
#endif
```

- 后果: 正常充电进入 CC 后 **8 秒**即报 `FAULT_CHARGE_TIMEOUT` 锁死，根本充不进电。
- 附带问题: 宏语义是**反的**——`test_mode` 分支反而给了更长的量产超时，命名极易误用。

**修复建议:** 默认宏直接给量产值（8h/3h）；调试用的短超时改成显式独立宏（如 `CHARGE_CC_TIMEOUT_TEST_MS`）并仅在明确定义了 `DEBUG_FAST_CHARGE` 类宏时才启用。不要依赖"未定义的 test_mode 取 0"这种隐式行为。

## 二、关键问题 (Critical)

### 🟠 C3 — 软件 OCP 阈值超量程，判据恒假（后备过流保护失效）

| 项 | 内容 |
|----|------|
| 位置 | `main.h:67-68,91`；`adc_dma.c:180-187`；`protect.c:88` |

电流换算量程计算（基于 `adc_raw_to_current`）:
```
满量程电流 = (VREF - V_offset) / (R_shunt × Gain)
           = (3.3 - 1.65) / (0.00333 × 20)
           = 1.65 / 0.0666 ≈ 24.8 A
```
而 `IOUT_OCP_A = 30A`，且 `adc_raw_to_current` 末尾 `(i < 0.0f) ? 0.0f : i` 把负电流钳到 0，`iout_a` 物理上不可能超过 ~24.8A。

- 后果: `protect.c:88` `if (g_adc_multi.iout_a > IOUT_OCP_A)` **永远为假**，软件后备 OCP 形同虚设。一旦发生模拟限流失效，MCU 不会兜底。
- （注意: 模拟硬件限流仍是第一道防线，但 MCU 软件后备必须有效才有双保险意义。）

**修复建议:** 将 `IOUT_OCP_A` 降至量程内（如 22A，留余量）；或调整 `IAMP_GAIN` 让 ADC 量程覆盖 30A+。同时把 `IAMP_GAIN` 从"待标定"尽快完成台架标定（见 Minor m4），否则 OCP/OVP 基准都不可信。

---

### 🟠 C4 — 过温保护全被注释 + 温度采样被禁用（无任何温度安全）

| 项 | 内容 |
|----|------|
| 位置 | `protect.c:93-97`（四路过温整段注释）；`adc_dma.c:189-209`（NTC 换算 `#if 0`）；`adc_dma.c:37-40`（ADC 仅扫 5 通道，温度通道未入扫描）；`main.h:125-151`（T_SENSE_* 引脚已定义但未使用） |

- 现象: 四路过温保护（PFC MOS / LLC MOS / 变压器 / 外壳）**整段被 `//` 注释**；NTC 换算函数 `ntc_raw_to_temp_c()` 被 `#if 0` 屏蔽；ADC 扫描序列只有 AC/BUS/VOUT/ISENSE/VBT 5 个通道。
- 后果: 固件**读不到任何温度**，既无过温保护也无降额。对 1.5kW 功率产品，长时间过温会烧毁器件且无预警。

**修复建议:** 这是必须补回的功能，不是"待定"项。
1. ADC 扫描序列补入 4 路温度通道（main.h 已定义引脚/通道）；
2. 恢复 `ntc_raw_to_temp_c()` 并校准；
3. `protect.c` 中加**带迟滞的去抖过温判据**（进入 95°C 触发、退出需低于 85°C，参考 LIMA48V 的迟滞设计），参考项目已验证这套逻辑可用。

## 三、主要问题 (Major)

### 🟡 M1 — 故障永久锁死，无运行时恢复、无看门狗

| 项 | 内容 |
|----|------|
| 位置 | `protect.c:48-55`（clear 函数）、`llc_control.c:141-146`（FAULT 处理）、全工程无 `fwdgt`/`wwdgt` 调用 |

- `protect_clear_fault()` 只被 `main.c` 启动预检调用一次；主循环、状态机、CAN 命令处理**从不调用**。
- 进入 `MAIN_STEP_FAULT` 后只做 `outputs_off()` + 红灯常亮并 `return`，**无 auto-retry、无"enable=0 清故障"通路、无故障计数恢复**。`MAIN_STEP_FAULT` 是终态，必须断电复位。
- 全工程**没有独立看门狗（IWDG）**，主循环死机无法自恢复。

**修复建议:** 
1. 区分**可恢复告警**与**不可恢复故障**（参考 LIMA48V 的 `WARING` 状态：关闭输出后立即回待机可重试）。
2. 增加恢复路径：收到 `enable=0` 或专用清故障命令时调用 `protect_clear_fault()` 并经安全时序重回 STANDBY。
3. 启用 IWDG 在主循环喂狗，作为死机兜底（功率产品必备）。

---

### 🟡 M2 — 软启动/斜率限制宏已定义却从未使用，基准瞬时阶跃下发

| 项 | 内容 |
|----|------|
| 位置 | `main.h:178,180-187`（`PWM_DUTY_SLEW` / `LLC_SOFTSTART_*`）；`llc_control.c` `apply_references()` + PRECHARGE 转移 |

- 宏都已定义：`PWM_DUTY_SLEW=0.002`、`LLC_SOFTSTART_DURATION_MS=500`、CV/CC 的起始/目标占空比全部就绪。
- 但 `apply_references()` 是**瞬时阶跃**把目标占空比写入 PWM；PRECHARGE → CC 转移时 `pfc_is_ready()` 后立即 `apply_references()` + `LLC_EN` 拉高。
- 后果: LLC 使能瞬间把完整 CV/CC 基准阶跃给模拟 IC，**存在输出过冲/浪涌风险**，软启动宏成了死代码。

**修复建议:** 用斜坡函数（基于 `PWM_DUTY_SLEW` 或 `LLC_SOFTSTART_*`）在使能后按 500ms 把占空比从 MIN 爬到目标值，再闭合输出继电器。

---

### 🟡 M3 — 母线过压、AC 输入保护缺失

| 项 | 内容 |
|----|------|
| 位置 | `pfc_control.c:66-70`（仅母线 UVP 304V）、`main.c`/`adc_dma.c`（ac_vol_v 已算但无判据） |

- 只有母线**欠压**保护（<304V 持续 200ms → `FAULT_BUS_UVP`）。
- 380V 母线**无软件过压保护**（无 `BUS_OVP`）。
- `ac_vol_v`（交流输入 RMS）已在 `adc_dma.c:149` 算出，但**没有任何地方拿它做 AC 欠压/过压保护**。

**修复建议:** 增加母线 OVP（如 >420V）、AC 欠压（<165V）与 AC 过压（>285V）判据，参考 LIMA48V 的 AC 输入保护状态机（带持续去抖 + 降额/关断分级）。

---

### 🟡 M4 — 温度降额定义但未实现（与 C4 同源）

| 项 | 内容 |
|----|------|
| 位置 | `main.h:75-77`（`TEMP_DERATING_START_C=65` / `TEMP_DERATING_FULL_C=85`）全工程零引用 |

- 降额参数已定义，但因为温度根本没采样（C4），既没有降额也没有过温保护。
- 后果: 高温环境下电流/功率不降额，器件热应力无上限。

**修复建议:** 修复 C4 拿到温度后，按 65°C 起降、85°C 全降的电流/电压降额逻辑（参考 LIMA48V 的 80%→60%→1A 多级降额）。

## 四、次要问题 (Minor)

### 🟢 m1 — CAN 状态帧浮点→uint8 越界强转（未定义行为）

| 项 | 内容 |
|----|------|
| 位置 | `can_comm.c:111,113,117` |

```c
tx_msg.tx_data[0] = (uint8_t)(g_adc_multi.vout_v * 10.0f);   // 58V→580.0f, 转 uint8 是 UB/截断
tx_msg.tx_data[1] = (uint8_t)((uint16_t)(...vout_v*10...) >> 8);  // 这一行写法才正确
```
`data[0]` 直接把 580.0f 转 `uint8_t`（浮点超范围转换是 C 未定义行为），应改为 `(uint8_t)((uint16_t)(v*10) & 0xFF)`。三处（vout/iout/vbat）的 `data[0]` 都有此问题，`data[1]` 写法却正确，**前后不一致**。

**修复建议:** 统一用 `uint16_t` 中间量再拆分低/高字节。

---

### 🟢 m2 — `s_rx_cmd` 结构体撕裂读（竞态）

| 项 | 内容 |
|----|------|
| 位置 | `can_comm.c:84-89`（ISR 写）、`can_comm.c:122-129`（主循环拷贝 `*out = s_rx_cmd`） |

CAN 中断优先级 3（最低中断优先级，但仍高于主线程）可在主循环 `can_comm_get_cmd()` 拷贝 `s_rx_cmd` 中途打断并改写，产生**撕裂读**。低概率但真实存在。

**修复建议:** 拷贝前 `__disable_irq()/__enable_irq()` 包住；或用双缓冲 + 单 flag 切换。

---

### 🟢 m3 — 3.3V 启动自检定义了却没做

| 项 | 内容 |
|----|------|
| 位置 | `main.h:305-306`（`ADC_STARTUP_V3V3_MIN/MAX_V`）；`adc_dma.c` 扫描序列无 3V3 通道 |

自检宏已定义，但 ADC 扫描序列只有 5 通道（无 3V3），`adc_startup_check()` 不校验 3.3V 供电。自检不完整。

**修复建议:** 若硬件有 3V3 采样通道则加入扫描与校验；否则删除这两个无效宏，避免维护者误以为已做。

---

### 🟢 m4 — 死代码 / 误导常量 / 待标定项

| 项 | 内容 | 位置 |
|----|------|------|
| `CC_CV_PWM_PIN_CONFLICT = 1U` | 名为"引脚冲突"却置 1，但 CV_PWM=PA8/TIMER0、CC_PWM=PA0/TIMER1 物理不冲突，宏纯属误导 | `main.h:167` |
| 一批零引用常量 | `VOUT_CC_V / VOUT_CV_V / VBUS_MIN_START_V / IOUT_SOFT_START_A / RUN_OK_LOW_V / RUN_OK_HIGH_V` 定义了从不使用 | `main.h:81-92` |
| 未发送的协议帧 | `CAN_ID_CHARGER_CMD(0x1800)` 定义但从不发送；`can_tx_data_t` 结构体未使用（`can_comm_tx_status` 是直接拼字节） | `can_comm.h`,`can_comm.c` |
| 待标定项影响保护精度 | `IAMP_GAIN=20 待标定`、`v_offset=VREF/2 待标定`、`FAN_CS_*` 待标定——直接决定 OCP/OVP 判据准确性 | `main.h:62,68`、`adc_dma.c:185` |
| 注释与代码不一致 | `pfc_control.c` 注释"NCP1654 软启 ~50ms"，实际等 100ms；`0.8` 系数无说明 | `pfc_control.c` |
| `ADC_CHANNEL_QTY=5` | 旧注释写"10 通道"未同步 | `main.h:153` |

**修复建议:** 量产前完成 `IAMP_GAIN`/`v_offset` 台架标定；清理死代码与误导宏；统一注释。

## 五、做对的地方（亮点）

评审不是只挑刺。以下设计是合理且可保留的:

1. **节拍握手干净** (`main.c:82-91,124-138,295-300`): 中断只置"最新一次"标志、主循环原子取走、记录丢拍，不补跑积压节拍，时序稳健。
2. **Fail-safe 及时断电** (`protect.c:57-66`): `protect_set_fault()` 立即断三路输出（OUT_RELAY/LLC_EN/PFC_RELAY），不等下一拍。
3. **状态机枚举完整** (`main.h:276-302`): 9 个主状态 + 12 个故障类型定义清晰，`enter_state()` 记录进入时间戳便于超时判断。
4. **AC RMS 方差法去直流偏置** (`adc_dma.c:118-161`): `RMS = sqrt(E[x²] - E[x]²)` 思路正确，避免 REF_1V65 偏置误差。
5. **`g_ms` 原子读 + `elapsed_reached()` 健壮**: 32 位对齐读写在 Cortex-M4 上原子，即使掉拍超时判断仍准确。
6. **分层职责清晰**: PFC/LLC 闭环交给模拟 IC，MCU 只做监控/保护/时序/CAN，符合该芯片算力定位。

## 六、修复路线图（建议优先级）

```
阶段一：让系统能跑起来（必须，阻塞级）
  ├─ C1  修正 CAN 帧格式/ID（标准帧改 ≤0x7FF 或改扩展帧）
  └─ C2  充电超时改回 8h/3h 量产值

阶段二：补齐安全保护（必须，功率产品底线）
  ├─ C3  OCP 阈值降到量程内（≤22A）
  ├─ C4  恢复温度采样 + 过温保护（带迟滞去抖）
  ├─ M1  故障分级恢复 + 加 IWDG 看门狗
  ├─ M2  实现软启动斜坡（消除浪涌）
  └─ M3  补母线 OVP + AC 欠/过压保护

阶段三：完善与清理（量产前）
  ├─ M4  温度降额逻辑
  ├─ m1  CAN 状态帧字节拆分修正
  ├─ m2  s_rx_cmd 撕裂读保护
  ├─ m3/m4 3.3V 自检 + 标定 + 死代码清理
```

**一句话总结:** 框架是对的，但当前固件处于"能编译、跑不起来、跑起来也不安全"的状态。按 C1→C2→C3→C4→M1 顺序修，系统才能既工作又安全。
