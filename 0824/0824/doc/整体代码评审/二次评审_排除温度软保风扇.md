## 一、仍存在的真实问题（按严重度）

### 🔴 S1（原 C1）CAN 帧格式与 ID 不匹配 —— 阻断 CAN/BMS 模式
**位置**：`can_comm.h:6-8`、`can_comm.c:56-67`、`:107-108`、`:83`

- `can_comm.h` 定义的三个 ID `0x1801 / 0x1802 / 0x1800` 是 **29 位 J1939 PGN 地址**（注释也写了"J1939"）。
- 但 `can_comm.c:108` 发送时 `tx_ff = CAN_FF_STANDARD`（11 位标准帧），`:83` 接收判定 `rx_sfid == CAN_ID_BMS_CONTROL`。
- **矛盾点 1**：11 位标准帧 ID 最大 `0x7FF`(2047)，而 `0x1801 = 6145` 超出范围。库会把高位置零 → 实际发出的 ID ≈ `0x1801 & 0x7FF = 0x001`，与 BMS 期望完全对不上。
- **矛盾点 2**：若 BMS 按 J1939 发 **29 位扩展帧**，而本端过滤器 `filter_mode=MASK`、`filter_bits=32BIT` 且未设 IDE 位（标准帧），**IDE 不匹配，帧直接被硬件丢弃**，永远收不到。
- **矛盾点 3**：过滤器移位错误。`filter_list_high = (CAN_ID_BMS_CONTROL << 5) & 0xFFFF`。32 位标准帧过滤器要求 STID 置于 bit[31:21]（即左移 21）；即便按扩展帧，EXID 也应左移 3 且置 IDE 位。左移 5 在两种模式下都不正确。

**结论**：当前 bench 模式因 `can_comm_init()` 被注释，**不影响调试**；但一旦启用 CAN/BMS 模式，收发都通不了。修复方向二选一：
- 方案 A（推荐，符合 J1939 习惯）：改用扩展帧 —— 发送 `tx_ff = CAN_FF_EXTENDED` + `tx_efid`，接收比较 `rx_efid`，过滤器按扩展帧布局（EXID<<3、置 IDE 位）。
- 方案 B：改用 11 位标准帧，把 ID 改为 `< 0x7FF` 的自定义值（如 `0x100/0x101`），并修正过滤器移位。

### 🔴 S2 CAN 命令未接入活动状态机路径 —— CAN 模式"接不通"
**位置**：`llc_control.c:234-348`（活动版）、`:350-471`（仅 `#if 0` 的 `_can` 版）

- 处理 BMS 命令（`can_comm_get_cmd`）、CAN 超时锁故障（`can_comm_timeout`）、周期上报状态（`can_comm_tx_status`）**全部只写在 `#if 0` 的 `power_supervisor_tick_1khz_can` 里**。
- 当前实际运行的 `power_supervisor_tick_1khz`（`:234`）**完全不碰 CAN**。
- 后果：即使 S1 修好、把 `can_comm_init()`/`can_comm_poll()` 打开，充电机也**不会接收 BMS 命令、不会因 CAN 超时保护、不会回报文** —— 等于 CAN 没接线。

**修复方向**：把 `_can` 版里的 CAN 处理段（取命令→设基准→使能；超时判故障；周期上报）合并进活动版 `power_supervisor_tick_1khz`，同时保留活动版已有的"FAULT 先恢复判定"逻辑（见下条 S4 相关）。注意合并时避免 `_can` 版里 `B2` 那种"FAULT 在 CAN 处理后才 return、return 后不再收命令"的陷阱（那属于软件保护恢复范畴，本次不深挖，但合并时要注意）。

### 🟠 S3 STANDBY 同 tick PFC 断-开 → 继电器抖动
**位置**：`llc_control.c:250-259`

```c
case MAIN_STEP_STANDBY:
    outputs_off();                 // 内部 pfc_disable() → 继电器复位、state=OFF
    ...
    if (s_enable_requested && g_adc_multi.vbat_v >= BATTERY_PRESENT_V) {
        pfc_enable();              // 同一 tick 又把继电器置位
        enter_state(MAIN_STEP_PRECHARGE);
    }
```

- 当 `enable` 已请求、但 `vbat_v < 10V`（电池未接入或电压不足）时，每 1ms 走一次 `outputs_off()(断)→pfc_enable()(合)`，PFC 继电器在 OFF/RELAY_ON 间**每毫秒翻转一次**，存在继电器粘连/寿命风险。
- 修复：`pfc_enable()` 本身有 `if (s_pfc_state == PFC_STATE_OFF)` 守卫，但 `outputs_off()` 每 tick 先把它打回 OFF，导致守卫永远重新触发。应在进入 STANDBY 时只关一次，或在 STANDBY 内仅当尚未进入 PRECHARGE 且 PFC 为 OFF 时才允许 `pfc_enable`，不要每 tick 先 disable 再 enable。

### 🟡 S4 PRECHARGE 超时故障码名不副实（诊断困难）
**位置**：`llc_control.c:272-274`

```c
else if (elapsed_reached(s_state_started_ms, PFC_READY_TIMEOUT_MS)) {
    protect_set_fault(FAULT_BUS_UVP);   // 实际是"母线 3s 没建起"，不是母线欠压
}
```
- 这里报 `FAULT_BUS_UVP`，和 `pfc_control.c:64/79` 真实的母线欠压共用同一故障码，现场无法区分"PFC 没起来"还是"母线真掉压"。
- 建议新增 `FAULT_PFC_READY_TIMEOUT` 专用码，便于诊断。功能上 A1（永久卡死）已通过此超时分支**修复**，仅命名需优化。

### 🟡 S5 头注释与实现的 CC/CV 基准矛盾（需确认设计意图）
**位置**：`llc_control.c:5-9` vs `:268`（仅此处调一次 `apply_references()`）

- 头注释写"CC 模式: CC_PWM=目标电流, CV_PWM=电压上限；CV 模式: CV_PWM=目标电压, CC_PWM=电流上限"，暗示 MCU 应在进 CV 时**切换基准**。
- 代码实际只在 PRECHARGE→CC 调一次 `apply_references()`，CC/CV 全程用同一组固定设定点，从不重设。
- 判定：若模拟 IC 内部用双环 `min()` 做 CC/CV 切换（常见架构），则"设一次两组基准"是**正确**的，问题仅在于头注释误导维护者；若模拟 IC 要求 MCU 在交叉点切换哪路 PWM 有效，则是**真 bug**。
- 建议：对照模拟 IC 数据手册确认，并统一注释。严重度低（设计澄清）。

### ⚪ S6 `LLC_START_TIMEOUT_MS` 命名与用途不符
**位置**：`llc_control.c:29`、`:300-303`
- 宏名"LLC 启动超时"，实际用于"CC 后 1.5s 输出未建起 → 报 BUS_UVP"。建议改名 `CC_OUTPUT_BUILD_TIMEOUT_MS`，且同样建议用专属故障码而非 `FAULT_BUS_UVP`。

### ⚪ S7 次要 / 健壮性
- **C5（outputs_off 不复位 PWM 占空比）** `llc_control.c:113-118`：断输出时不把 `CV_PWM/CC_PWM` 复位到 `INIT`。功能上因下次 PRECHARGE→CC 会重调 `apply_references()`，不致命；但为稳妥可在 `outputs_off()` 末尾复位占空比，确保重充从安全值起步。
- **C6（TRICKLE/INVALID 走 default→STANDBY）** `llc_control.c:343-346`：枚举若存在 `MAIN_STEP_TRICKLE` 且未来被置位，会被 default 直接打回 STANDBY，属未实现特性。当前无状态会进入 TRICKLE，暂不触发。

## 二、本次确认已修复 / 原本就正确的点（给个定心丸）

- ✅ **A1 PRECHARGE 永久卡死**：已新增 3s 超时分支（`llc_control.c:272`），母线建不起会进故障，不再卡死。
- ✅ **B3 CC/CV 超时 8s/3s**：当前 `main.h:108-109` 为 8h/3h，正确（旧文档的 8s/3s 是过期内容）。
- ✅ **PFC 母线 OVP**：`pfc_control.c:71-74` 已有，带 去抖，原"缺失"结论有误。
- ✅ **串口 SET 命令**：`sscanf` 使用正确，命令可解析（原"scanf 误用"误报）。
- ✅ **PWM 生成 `pwm_llc.c`**：`cv_pwm`/`cc_pwm` 均有占空比 `f_clampf` 限幅、影子寄存器缓冲（更新无毛刺）；TIMER0 高级定时器已 `primary_output_enable`。干净，无问题。
- ✅ **主循环 `main.c`**：SysTick/TIMER3 用"仅保留最新待处理标志 + 丢节拍计数 + `__disable_irq` 原子取走"模式，无背靠背补采、无阻塞、无重入风险；ADC 用 DMA 循环 + `copy_if_ready`(FTF 标志同步)，多任务采样同步正确。架构稳健。
- ✅ **AC RMS 算法**：`adc_dma.c:117-140` 采用 `RMS = sqrt(E[x²])`，注释说明对"全波整流单极性波形"不减去均值平方是对的；5kHz 采样、1000 点(200ms)窗口。正确。
- ✅ **PFC 子状态机恢复**：`PFC_STATE_FAULT` 内 `pfc_disable()` 会把 `s_pfc_state` 置回 `PFC_STATE_OFF`，配合 STANDBY→PRECHARGE 流程可重新使能，内部状态能自恢复（充电机级恢复依赖 CLEAR，属软件保护范畴，本次不评）。
